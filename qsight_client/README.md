# Q.sight (개인용 웹)

AI 챗봇 상담 → 약정 항목 수집 → 전자서명 요청까지 이어지는 기부 플랫폼의 **개인용 웹**입니다.
React(Vite) 프론트엔드 + Node/Express 백엔드로 구성되어 있습니다.

개인용 웹은 **화면과 챗봇만 담당**합니다. 계약서 생성과 모두싸인 전자서명은 전부
**기업용 웹 서버**가 처리하며, 개인용 웹은 모두싸인 API를 직접 호출하지 않습니다.

```
브라우저 ──/api──▶ 개인용 서버(4000) ──▶ 기업용 서버(8090) ──▶ 모두싸인
                      │
                      └──▶ Upstage AI (챗봇 LLM)
```

기업용 API는 개인용 *서버*에서만 호출합니다. 브라우저는 기업용 서버를 직접 부르지 않으므로
CORS 문제가 없고, 기업용 API를 인터넷에 노출할 필요도 없습니다.

## 실행 방법

기업용 웹 서버가 먼저 실행되어 있어야 합니다 (기본값 `http://localhost:8090`).
그 다음 터미널 두 개로 server와 client를 각각 실행합니다.

### 1. 서버 실행

```bash
cd server
npm install
npm run dev
```

`http://localhost:4000` 에서 API 서버가 실행됩니다.

### 2. 클라이언트 실행

```bash
cd client
npm install
npm run dev
```

`http://localhost:5173` 접속 시 화면이 뜨고, `/api` 요청은 Vite 프록시를 통해 자동으로 서버(4000번 포트)로 전달됩니다.

## 환경변수 (server/.env)

| 키 | 설명 |
| --- | --- |
| `UPSTAGE_API_KEY` | 챗봇 LLM용 Upstage API Key |
| `UPSTAGE_BASE_URL`, `UPSTAGE_MODEL` | Upstage 엔드포인트 / 모델명 |
| `QSIGHT_CORP_API` | 기업용 웹 서버 주소 (기본 `http://localhost:8090`) |
| `MODUSIGN_EMAIL`, `MODUSIGN_API_KEY` | **개인** 모두싸인 계정 (증서함 조회 전용, 비워두면 증서함 목록만 비활성화) |
| `PORT` | 개인용 서버 포트 (기본 4000) |

유산기부 대본·질문·고지 문구는 환경변수가 아니라 `server/config/legacy-spec.json`에 있습니다
(아래 "유산기부" 참고).

계약서 생성과 서명 요청 메일 발송은 전부 기업용 서버가 **기관 계정** 키로 처리합니다.
개인용 웹의 모두싸인 키는 그와 다른 **개인 계정**이어야 하며, 조회 외에는 아무것도 하지 않습니다
(`server/src/lib/modusign.js`에는 문서 생성·서명요청 함수가 없습니다).

## 화면 흐름

```
1. 사업 목록      → GET  /api/programs                        (기업용 ①)
2. 사업 선택      → GET  /api/programs/{id}/contract-form      (기업용 ②)
3. 챗봇이 항목 수집 → POST /api/chat                            (외부 서명 API 호출 없음)
4. 수집 완료      → POST /api/agreements                       (기업용 ③ — 여기서 메일 발송)
5. 서명 대기 안내  → GET  /api/agreements/{id} 폴링             (기업용 ④, 10초 간격)
```

기부자는 iframe이 아니라 **이메일로 받은 모두싸인 링크**에서 서명합니다.

## 챗봇 동작

챗봇 질문 목록은 코드에 하드코딩되어 있지 않습니다. ②가 준 `fields`가 곧 체크리스트입니다.

- 남은 항목 = `fields` 중 `required=true` 이면서 아직 값이 없는 것. 이 차집합은 **서버 코드가 계산**하고, 완료 판단을 LLM에 맡기지 않습니다 (`server/src/lib/fields.js`)
- 시스템 프롬프트는 매 턴 `fields`로부터 조립됩니다 (`server/src/lib/prompts.js`)
- 항목 유형별 정규화: `number`는 숫자만 (`"3만원"` → `30000`), `select`는 반드시 `options` 안의 값, `check`는 `true`/`false`, `date`는 `YYYY-MM-DD`. 정규화에 실패한 값은 버려지고 챗봇이 다시 질문합니다
- 기관이 계약서 서식을 바꾸면 질문도 따라 바뀝니다. **③을 부르기 직전에 ②를 다시 조회해 `schema_version`을 비교**하고, 달라졌으면 메일을 보내지 않고 바뀐 항목만 다시 물어봅니다
- `signer.name` / `signer.email`은 `values`와 별개로 마지막 단계에서 따로 확인합니다

### 기관이 미리 채운 항목 (prefilled)

②는 항목을 두 갈래로 나눠서 줍니다. 기관이 서식에 값을 적어둔 항목은 `prefilled` /
`prefilled_labels`로 빠지고, `fields`에는 기부자가 채울 것만 남습니다.

- 챗봇은 `fields`만 물어보므로 기관이 정한 값은 질문 대상이 아닙니다
  (같은 key가 겹쳐 와도 `server/src/routes/chat.js`에서 한 번 더 걸러냅니다)
- 개인용 서버는 이 값을 들고 있다가 ③에 그대로 되돌려줍니다. 기업용이 최종적으로 다시
  덮어쓰므로 기부자가 같은 key로 무엇을 보내도 기관 값이 이깁니다
- 확인 화면에 "기관이 계약서에 미리 정해둔 항목"으로 함께 보여줍니다 (수정 불가)

## 기부자 기본정보 (로그인 대체)

별도 로그인 없이, 처음 들어오면 이름·이메일·전화번호를 한 번 입력받습니다 (`client/src/profile.js`).

- 값은 브라우저 `localStorage`에만 저장됩니다. 서버는 이 정보를 갖지 않습니다
- 계약 항목 스키마에서 이름·연락처·이메일에 해당하는 항목을 찾아 미리 채워두므로,
  **챗봇은 기본정보로 채워지지 않은 항목만 질문합니다**
- 항목 key를 코드에 박지 않고 key와 label을 함께 보고 짝을 찾습니다. 짚이는 항목이 없으면
  그냥 비워두고 챗봇이 평소대로 물어봅니다
- 마이페이지 또는 `/profile`에서 언제든 확인·수정할 수 있습니다

## 유산기부 (녹음유언)

유산기부만 정기기부와 다른 전용 흐름을 탑니다. 계획서는 `LEGACY_PLAN.md`입니다.

```
안내·동의 → 사업 선택 → 유산 전용 챗봇 → 대본 확인 → 의향 등록(서명)
          → 증인 등록 → 녹음 → 자가 확인 → 완료
```

서명(의향 등록)이 녹음보다 **앞에** 옵니다. 서명 요청 메일을 먼저 보내두면 녹음 도중
이탈해도 기부 의사는 기업용에 남기 때문입니다.

### 법률 의존 항목은 전부 JSON 한 파일에

대본 문안, 챗봇이 묻는 항목, 재산 특정 방식, 증인 결격 문항, 자가 확인 항목, 화면 고지 문구는
**`server/config/legacy-spec.json`에만** 있습니다. 화면에는 어떤 문구도 하드코딩하지 않습니다.

- 법률 검토 결과가 나오면 **JSON만 고치고 서버를 재시작**합니다. 프런트 재빌드는 필요 없습니다
- 클라이언트는 `GET /api/legacy/spec`으로 한 번 받아 모든 화면을 그립니다
- 기동 시 `server/src/lib/legacySpec.js`가 검증합니다. **하나라도 실패하면 서버가 뜨지 않습니다**
  1. 대본에 법정 요건 5종 태그(`donor_name` `date` `content` `witness_confirm` `witness_name`)가 모두 있는가
  2. `review_checklist`가 그 5종과 1:1로 대응하는가
  3. 대본 플레이스홀더가 전부 `collect`·재산 하위 항목·자동 생성 값에 있는가

  "오늘은 ○년 ○월 ○일입니다" 한 줄이 빠지면 유언이 통째로 무효가 되므로 조용히 넘어가지 않습니다.

### 대본은 LLM이 만들지 않는다

챗봇은 값을 수집할 뿐이고, 대본 문장은 **코드가 spec의 템플릿에 값을 끼워 넣어** 만듭니다
(`server/src/lib/legacyScript.js`). 재산 표현도 `bequest_types[].phrase` 템플릿을 씁니다
(`상속재산의 {{share_percent}}퍼센트`). 법정 요건 문장을 확률적 생성에 맡기지 않습니다.

`bequest_type`을 고르면 그 방식의 하위 항목이 질문지에 붙습니다(비율 → 퍼센트, 특정 재산 → 종류·표시).
**보험금**을 고르면 유언 경로가 아니라 "보험사에서 수익자 변경" 안내로 빠집니다.

### 질문지 = spec + 기관 **유산기부 신청서**

기부 의사 등록은 기존 약정 흐름(③)을 그대로 쓰므로 **기관 서식의 필수 항목도 결국 채워야 합니다.**
그래서 유산 챗봇의 질문지는 `spec.collect` + ②의 `fields`를 합친 것입니다
(`server/src/lib/legacySpec.js` — `chatFields`). 서명 화면에서 같은 항목을 또 입력받지 않기 위해서입니다.

②를 부를 때 **`?donationType=legacy`** 를 붙여 기관이 따로 등록한 유산기부 신청서를 받습니다.
정기기부 서식(회차 금액·납부 주기·약정 기간)은 유산 흐름에 아예 들어오지 않습니다.

- 같은 key는 한 항목으로 합칩니다. 형식·필수 여부는 기관 정의를 따르고(약정서가 그 형식을 요구),
  부르는 이름·선택지·질문 순서는 대화에 맞춘 spec 쪽을 씁니다.
  선택지가 spec 우선인 이유는 대본 조립과 직결되기 때문입니다 — "보험금"은 기관 서식에 없지만
  개인용에서 수익자 변경 안내로 빠지려면 선택지에 남아 있어야 합니다
- 기관이 미리 채워둔 항목과 `spec.derived`가 대신 채우는 항목은 질문에서 빠집니다
- 체크리스트에는 기관 서식에서 온 항목에 "약정서" 표시가 붙습니다
- **spec에 key를 새로 만들 때는 기관 서식의 key와 겹치지 않게** 지어야 합니다.
  뜻이 다른데 이름이 같으면 한 항목으로 합쳐집니다 (유증 금액을 `bequest_amount`로 둔 이유)

`spec.derived`는 기관 서식 항목 중 **코드가 대신 채우는 것**입니다. 지금은 신청서의 "특정 내용"에
대본과 같은 문구(`"상속재산의 10퍼센트"`)를 넣습니다. 기관이 key를 바꾸면 이 줄만 고치면 됩니다.

유산기부 신청서가 연결되지 않은 사업은 사업 목록에서 "유산기부 준비 중"으로 선택할 수 없고,
서버도 `LEGACY_FORM_NOT_READY`로 막습니다. 정기 서식으로 대신 받으면 안 되기 때문입니다.

의향 등록 화면은 그래서 입력칸이 없습니다. 대화에서 모은 내용을 확인만 하고, 서명 요청 메일이 갈
**서명자 이름·이메일만** 따로 받습니다(주소가 틀리면 요청이 엉뚱한 곳으로 가므로 눈으로 확인받습니다).

### 녹음

`MediaRecorder`로 브라우저에서 직접 녹음합니다.

- **파일 업로드 input이 없습니다** — 재생본·편집본이 들어오면 무효 사유입니다
- **일시정지가 없습니다** — 증인 진술이 따로 녹음되면 무효로 본 판례가 있습니다
- 중단하면 그 녹음은 올리지 않고 버립니다. 최대 10분, 녹음 중 페이지 이탈 방지
- 저장 시 **SHA-256 해시 + 그때 읽은 대본 전문 + spec 버전**을 함께 남깁니다

### 다시 녹음할 때 (중복 약정 방지)

녹음은 한 등록에 하나뿐이라(저장되면 잠긴다) 다시 녹음하려면 등록을 새로 만들어야 합니다.
그런데 실패한 것은 녹음이지 기부 의사가 아닙니다. **서명을 다시 하면 기업용에 같은 사람의
약정이 두 건 쌓이므로**, `POST /api/legacy/pledges/:id/redo`가 값·증인·대본 수정분과 함께
`agreement_id`·`document_id`를 그대로 물려받은 새 등록을 만듭니다. 서명 요청 메일은 다시 가지 않습니다.

- 두 레코드는 `supersedes` / `superseded_by`로 연결되고, 대체된 쪽은 마이페이지 목록에서 빠집니다
- 이미 등록을 마친 사람이 유산기부를 처음부터 다시 시작하려 하면 안내 화면에서 "이어서 하기"로 잡습니다
- 등록을 마친 뒤 서명 화면으로 되돌아와도 서버 기록을 먼저 확인해 다시 제출되지 않습니다
- **브라우저를 바꾸거나 저장소를 지우면** 이전 등록을 알아볼 수 없습니다(로그인이 없어 id를
  브라우저가 들고 있기 때문). 이 경우만 중복이 남고, 기업용에서 이름·연락처로 확인해야 합니다

### 저장 위치

| 엔드포인트 | 역할 |
| --- | --- |
| `GET /api/legacy/spec` | 대본·질문·고지 문구 |
| `POST /api/legacy/chat` | 유산 전용 챗봇 (질문지 출처만 다르고 규칙은 일반 챗봇과 같음) |
| `POST /api/legacy/pledges` | 등록 생성 (고지 동의 필수) |
| `GET`·`PATCH /api/legacy/pledges/:id` | 조회 · 값/대본수정/증인/자가확인 저장 |
| `POST`·`GET /api/legacy/pledges/:id/recording` | 녹음 저장 · 재생 |

레코드는 `server/data/legacy/<id>.json`, 녹음은 같은 이름의 오디오 파일입니다(`.gitignore` 처리됨).
**녹음 파일은 기업용에 보내지 않습니다.** 생전에 기관이 유언 내용을 열람하면 분쟁 소지가 되기 때문입니다.
로그인이 없으므로 등록 id는 브라우저 `localStorage`가 들고 있고, 마이페이지는 그 id로만 조회합니다.

## 데이터 보관

개인용 서버는 약정을 저장하지 않습니다. 약정 원본은 기업용 서버에 있고, 서명된 문서는 모두싸인에 있습니다.
증서함은 개인 모두싸인 계정으로 본인이 참여한 문서를 조회해 보여주고, 문서를 누르면
서명된 약정서 PDF를 미리보기로 확인할 수 있습니다.

## 모금이 종료된 사업

기업용에서 사업을 "보관"하면 기부자가 새로 선택할 수 없습니다. ①의 목록에서 빠지는 것에 더해,
개인용 서버가 ②·챗봇·③ 세 지점에서 ① 목록 잔존 여부를 확인하므로 **대화 도중에 보관된 경우에도**
안내 화면으로 막힙니다.

## 화면 구성

1. 온보딩
2. 기본정보 입력 (로그인 대체 — 이름·이메일·전화번호)
3. 메인 홈 (진행중인 모금 사업 요약)
4. 마이페이지 (기본정보 확인·수정)
5. 기부 유형 선택
6. 고향사랑기부 안내 *(접수 준비 중 — 지자체 데이터 연동 예정)*
7. 문화유산 후원 *(접수 준비 중 — 후원처 데이터 연동 예정)*
8. 유산 기부 — 전용 흐름 9화면 (안내·동의 → 사업 선택 → 챗봇 → 대본 확인 → 의향 등록 →
   증인 등록 → 녹음 → 자가 확인 → 완료)
9. 모금 사업 목록 (`contract_ready`가 false면 "준비 중"으로 선택 불가)
10. 챗봇 시작
11. 챗봇 대화 (기본정보 외 항목만 수집)
12. 입력 내용 확인 (LLM 없이 코드가 정리해 표시)
13. 서명자 정보 입력 → 약정 생성
14. 서명 대기 (10초 간격 상태 폴링)
15. 나의 증서함
16. 약정서 보기 (서명된 PDF 미리보기)
